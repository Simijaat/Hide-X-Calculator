# PR1 - Foundation + Private Calculator/Vault

## What was implemented
- Refactored `VaultSecurityManager.kt` to use PBKDF2 with HMAC-SHA256 for secure PIN hashing. Random salts are generated via `SecureRandom` and stored alongside hashes using Base64 encoding in `EncryptedSharedPreferences`.
- Added an inactivity timer and auto-lock logic to `VaultSecurityManager.kt`, monitored via a `lifecycleScope` coroutine in `MainActivity.kt`.
- Applied `FLAG_SECURE` to the `MainActivity` window to block screenshots and recent-task previews, adhering to Android security best practices.
- Enhanced the `CalculatorViewModel.kt` parser logic to natively handle division by zero (catching `Infinity` and `NaN`), added state management to distinguish between new calculations and active input (`isResult`), and introduced a functional `DEL` action.
- Built out a discrete, two-step PIN setup flow in `CalculatorViewModel.kt` triggered entirely within the calculator context (enter PIN -> `=` -> verify PIN -> `=`).
- Added the `DEL` button to the `CalculatorScreen.kt` UI layout.
- The `VaultScreen.kt` remains a scaffolded dummy screen ready to house feature tools.

## Important architectural decisions
- **Jetpack Compose**: Selected for a modern, scalable UI toolkit.
- **Hilt (Dagger)**: Essential for maintainable dependency injection, especially as the app grows with VPN, ad-blocking, etc.
- **EncryptedSharedPreferences**: Used for storing the vault PIN hash and salt. It leverages Android KeyStore for secure, encrypted local storage.
- **Security Logic**: Hardened by shifting from plaintext PIN storage to a PBKDF2 approach (100,000 iterations, 256-bit key).
- **MVVM Architecture**: ViewModels manage state, decoupling UI from business logic. StateFlows provide reactive security state to the Navigation graph to force lock-outs.

## Known Issues / Limitations
- Calculator logic uses a simple recursive descent parser which relies on Doubles and may encounter floating point inaccuracies for some advanced calculations.
- While `FLAG_SECURE` prevents screenshots, advanced rooting could still potentially inspect memory.

# PR4 - Advanced Link Resolver + Media/File Download Engine

## What was implemented
- **Data Layer**: Created `DownloadTask`, `DownloadState`, `DownloadDao`, and `DownloadDatabase` via Room to persist download queues and history. Bound securely via Hilt.
- **Link Resolver Architecture**:
  - Implemented modular `ResolverStrategy` interface.
  - Implemented `DirectLinkStrategy` using lightweight HEAD requests to detect exact file matches and raw downloads.
  - Implemented `HtmlMetadataStrategy` to scrape legitimate, standard OpenGraph (`og:video`) and Twitter Card URLs gracefully from supported sites.
  - Coordinated through `LinkResolverManager`.
- **Download Engine**:
  - Created `SecureDownloadService` mapped as a `dataSync` Foreground Service to ensure reliability across app states.
  - Handled persistent, chunked file downloading securely to internal sandbox (`context.filesDir/vault_downloads`).
  - Supported Range headers for pausing/resuming.
  - Validated download integrity by mapping content-length accurately.
  - Managed concurrent tasks via Coroutines (`Dispatchers.IO`).
- **File Export**:
  - Created `DownloadStorageManager` using `MediaStore` to securely export completed downloads out of the Vault sandbox into the public Android `Downloads/VaultExport` directory on explicit user request.
- **UI/Browser Integration**:
  - Created `DownloadCenterScreen` for queue management (pause, resume, delete, export).
  - Created `ResolverDialog` to let the user select between multiple resolved media options.
  - Bound `BrowserScreen` WebView to intercept `setDownloadListener`, instantly piping native download requests directly into the `DownloadCenterScreen`.
  - Added system intent sharing (`ACTION_SEND`) to `MainActivity` to allow users to directly share links from external apps to the Vault's Resolver pipeline.

## Important architectural decisions
- **Service Type**: Used `dataSync` foreground service to allow the download engine to run reliably without being killed immediately by Android's battery optimizer.
- **Resolver Pipeline**: Separated resolution from downloading. A link must be successfully converted to a `DownloadOption` before a task is enqueued. This avoids fake states.
- **Temporary Files**: Downloads write to `.part` files in internal storage until successful completion to prevent partial, broken files from being consumed by the user or the app.
- **No DRM circumvention**: The resolver relies strictly on standard HTTP headers, standard HTML tags, and accessible URIs, making no attempt to defeat protections.

## Validation Performed
- Repository builds cleanly via `./gradlew clean assembleDebug`.
- Lints and tests passed via `./gradlew clean test lint check`.
- Verified StateFlow logic inside navigation graph to dynamically pick up shared URLs.

## Known Issues / Limitations
- HLS/M3U8 streaming manifests are not supported by this basic byte-chunk downloader.
- Websites requiring Javascript-rendered DOM evaluation will fail the basic `HtmlMetadataStrategy`.
